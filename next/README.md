# Terminal Sessions 2.0

> 2.0 lives in `next/`, beside the 1.x code this package has shipped so far. Both are in the package: `termd`, `tsm` and `tsm-relay` are 2.0; `terminal-sessions-mcp`, `session-server` and `session-cli` are 1.x. 2.0 changes one thing 1.x does: its graceful kill hangs up every process on the session's terminal once the shell is gone, as `close` does. Otherwise, what reaches 1.x is the package they share: a narrower Node range (`engines`), `npm run build` and `npm test` building 2.0 too, and 2.0's two dependencies installing with it. The lockfile also moves `@types/node` from 20 to 22, and `express-rate-limit`, `hono` and `ip-address` up a patch release each. The design discussion is [antra-tess/terminal-sessions-mcp#11](https://github.com/antra-tess/terminal-sessions-mcp/pull/11).

Persistent shells for agents. Each session is your own login shell, kept alive by a daemon between calls, connections and host restarts. bash, zsh and fish start with your startup files and get the session's integration; any other shell starts with no arguments and runs without it (see [What it can't tell](#what-it-cant-tell)). An agent types into it only by explicit calls, gets the exit status, duration and directory of each command `run` types in an integrated shell, with its output (a command that ends the shell, such as `exit 17`, gets the shell's exit instead), and is woken only when something needs it: a command ended that no call was waiting on, a program is waiting for input, a shell died, or a pattern it asked for appeared.

It speaks MCP to any MCP host, and MCPL to hosts that support it (agent-framework, and Claude Code through `mcpl-cc-bridge`), for the wakes.

## Quick start

```bash
npm install -g term-sessions-mcp     # bins: termd, tsm, tsm-relay
tsm open demo
tsm run demo 'echo hello; pwd'
```

Then connect a host with one of the configurations in [`next/config/`](config/): each launches `tsm-relay` over stdio. Nothing needs to be started first: the first relay or `tsm` that finds no daemon starts one.

## What an agent gets

Eight tools. The results of `open`, `run`, `send`, `look`, `read` and `stop` open with the session's status line, such as `[main · command 3 · exit 0 · 1.2 s · at the prompt · /home/u/app]`: the command and how it ended, what is in front of the shell now, and the directory. `list` gives a line for each session, and `close` says how the shell ended. A refused call says why, and opens with the status line only when what is in front of the shell is the reason.

| Tool | |
|---|---|
| `open(name, cwd?, cols?, rows?)` | Opens a session. No other tool opens one, so a mistyped name is refused rather than run in a fresh shell. |
| `run(name, command, wait?, notify_on?)` | Runs one command line, only at the prompt; otherwise nothing is typed and the refusal says what is in front. Returns the status and output, or "still running" when the wait ends; on a host that takes wakes, the end is reported when it comes. `notify_on` reports a pattern in its output once: in the result if the command has ended, otherwise as it appears. Its `structuredContent` gives the same as values; see below. |
| `send(name, text?, keys?, wait_for?, wait?)` | Types exactly the text and named keys, nothing appended, for a program waiting for input or a full-screen one. Returns the new lines, or the screen, once `wait_for` matches or output is quiet. Arrows follow the cursor-key mode the program set. |
| `look(name, until?, match?, wait?)` | What you haven't seen yet, and what is in front now; with `until: "end"`, `until: "input"` or `match`, after waiting for it. `until: "end"` also returns when a program in front waits for input, since it won't end until answered. |
| `read(name, command?, lines?, match?, context?)` | Earlier output: a command's output by id or a range of lines, not both, or matching lines with context, cut like every result, so long output is read in ranges. |
| `stop(name, signal?)` | Ctrl-C typed to the terminal, so it reaches whatever is in front, a shell's own loop included; then TERM, then KILL to the job in front, each step reported. TERM and KILL never go to the shell. |
| `list()` | Each session, what is in front of it, its directory, and reports you haven't seen. With many sessions, rows give way so the oldest report still shows. |
| `close(name, force?)` | Hangs up the shell. Returns the session's reports you haven't seen, since nothing shows them after. |

- **Waits** default to 15 s and stop at 55 s, under agent-framework's 60 s deadline for a call. A `read` search, and `run`'s `notify_on` search of output already there, stop at 55 s too, and say which lines they left. No call holds longer.
- **A cancelled call** answers nobody. What it took is reported as though no call had, unless another call's result showed it or a later report about its command came. A wait for input that is over isn't reported. A call that fails after taking something reports it the same way. A cancelled `run`'s command keeps running, and its `notify_on` still reports.
- **Long output** keeps its start and its end within 24,000 characters, agent-framework's inline limit for a tool result, and says how to read more: `read` gives a command's output or a range of lines, cut the same way. A single line longer than that is cut in its middle, and no call returns the middle.
- **`run`'s `structuredContent`,** for a script, holds `command`, `front` and `running`, and:
  - `exitCode`: the command's status. It is `null` with `running: true` while the command runs, and `null` with `running: false` when no status is known: a shell without the integration, a removed hook, or the shell exiting mid-command. A non-zero status is a result, not `isError`.
  - `output`: the command's own lines joined by `\n`, never the status line, the typed command or the text's notes. It is whole when it fits the budget the text has for it; otherwise it keeps the start (a third) and the end, and `outputLeftOut` gives `at`, where in `output` the left-out part belongs, and `characters`, how much was left out. Both count UTF-16 code units, as every budget here does, and the cut never splits a surrogate pair, so a script that indexes by code point is off by one for each character outside the Basic Multilingual Plane before `at`. `read` with a range of `lines` within the command's gives the rest. `outputDropped` counts the earliest lines the session no longer keeps, when there are any. While the command runs, `output` is what it has printed so far, and its last lines may still change on the screen. In a shell without the integration it holds the same lines the text shows, which the session ends at the shell's next prompt rather than at an end mark.
- **A full-screen program's screen** fits one result whole when each cell is one UTF-16 unit and the result's other lines fit the 1,000 characters kept for them. Wider text (emoji, combining marks), or many commands ending during one `send`, loses top rows, and the result says how many.
- **Wakes** (MCPL, feature set `terminal.events`) carry the status line and the last 20 lines or the screen, one tag each: `terminal:ended`, `terminal:waiting`, `terminal:exited`, `terminal:match`; a match's wake carries its matched line instead. A report no host took stays for `list` and `look`; one about a command goes once the session no longer keeps that command. It keeps its last 10,000, and fewer when their text passes 6 Mi characters. Plain MCP hosts get no wakes; `look` with `until` is how they wait.
- **Scopes:** the relay's `--scope` names the sessions a host sees, so two agents' `main` are two shells. Two hosts given the same scope share its sessions and their wakes: a wake is pushed to each host not still answering an earlier one, and to a busy one later only if no host has taken it by then.
- **`close`** hangs up the shell and every process on its terminal. That includes disowned jobs and jobs whose parent exited, whatever the shell's own settings, such as zsh's `NO_HUP`. A process that left the terminal with `setsid` outlives it. So does a job started with `nohup`, which ignores the hangup. `close` with `force` KILLs the shell, every process on its terminal and every process the shell started. Only a process that left the terminal and is no longer the shell's descendant outlives it.
- **Environment:** every session's shell starts from the daemon's environment, minus the launching terminal's identity, Volta's and npm's launch variables, agent hosts' session variables and this package's own, with Volta's internal image directories taken off `PATH`, and it is the same for every scope. When the shipped unit or launch agent runs the daemon, or a relay starts it as a transient systemd unit, that is the user manager's or launchd's environment, not the relay's; when a relay or `tsm` starts it detached, it is the environment of whichever started it. Other state of whatever started it stays, such as an activated virtualenv's. The shell's startup files run on top of it. Scopes keep sessions apart, not credentials: they are one user's shells.

## What it can't tell

- **A shell without the integration** gives no statuses: it counts as at its prompt once its output is quiet and it waits at the terminal (its line editor holds it, or the shell reads it itself), and a command's status is "unknown". Output after a command's last line break shares a line with the next prompt, and is left out. A builtin `read` waiting at the terminal looks the same as the prompt there, so `run` types into it; answer it with `send`. The terminal may echo a multi-line command's later lines, and those can show in its output. Inside an `ssh` someone typed, what is in front is `ssh`, and what is typed there gets no statuses either. For statuses on another machine, run the relay there: `ssh box tsm-relay --scope NAME`.
- **A command typed through `send` that removes both the session's prompt hook and its prompt mark** (`unset PROMPT_COMMAND; PS1="> "` in bash, `precmd_functions=(); PS1="> "` in zsh) leaves the session unable to see its prompt: it shows the shell itself running and refuses `run`. `close` the session and `open` it again. A command given to `run` in bash or zsh gets the hooks put back after it, except a zsh command that leaves a heredoc without its terminator (below). A command typed through `send` that removes only the prompt hook leaves the prompt seen, with that command's status unknown.
- **Waiting for input** is the kernel's evidence: on Linux, a program blocked reading this terminal. A program that waits in `poll`, such as Python's REPL or `ssh`, shows as running. So does a 32-bit program on a 64-bit Linux kernel: its system calls use another numbering. macOS shows no such evidence, so there it is always "running", and the status line says it can't tell.
- **End marks** carry a chained nonce: a mark's counter is spent once used, so output that replays an old mark is refused. A program that reads the shell's own variables can print a mark with the live nonce, deliberately, and is not defended against. Output never shows a recent nonce. It shows `[redacted]` in its place, padded with dots to the nonce's length.
- **A daemon restart ends every shell.** A host that reconnects is told no session it names is open.
- **bash isn't started in login mode,** since a login bash ignores the file that installs the session's hooks. It reads the files a login shell reads, in their order (`/etc/profile`, then the first of `~/.bash_profile`, `~/.bash_login` and `~/.profile`), but `shopt login_shell` is off and `~/.bash_logout` doesn't run. zsh and fish start as login shells.
- **fish 3 keeps a command given to `run` out of its history.** fish 4 adds it, as typing it would.
- **In zsh, a heredoc left without its terminator** in a command given to `run` takes the session's own lines after it as its body: they print, or go into the file the heredoc writes, and the hooks aren't put back after that command.
- **In bash, while a command given to `run` runs,** its RETURN trap is the session's, which keeps the pipeline's statuses. `trap -p RETURN` shows it there, and the shell's own trap comes back afterwards.

## Running the daemon

One daemon per user holds every shell, on a Unix socket in a directory only you can enter: `$XDG_RUNTIME_DIR/terminal-sessions/daemon.sock`; where that variable isn't set, `/run/user/<uid>/terminal-sessions/daemon.sock` on Linux when that directory is yours alone; otherwise `/tmp/terminal-sessions-<uid>/daemon.sock`. A relay that finds none starts one: on Linux, as a transient systemd user unit where one can be started, so the daemon outlives a host whose service stops; elsewhere, or where `systemd-run` fails, detached, in the starter's control group, with its output in `daemon.log` beside the socket. To have it started again after a crash, install `next/config/termd.service` (systemd) or `next/config/com.animalabs.termd.plist` (launchd). Either keeps the daemon across logins only where the user's service manager outlives a logout, which on Linux takes lingering (`loginctl enable-linger`); on macOS a launch agent stops at logout. Start the systemd unit (`systemctl --user enable --now termd`) before any relay starts a daemon, or after `tsm daemon stop`. Its daemon exits when it finds another already answering, and `Restart=on-failure` doesn't start it again. The launch agent's `KeepAlive` starts it again every 10 seconds, so it takes over once the other daemon ends.

`tsm daemon stop` asks it over its socket to stop, ending every shell, and returns once the socket no longer answers; it sends no signal, and names the daemon's pid if it doesn't stop. Under the shipped launch agent, launchd starts it again (`KeepAlive`); `launchctl bootout gui/$(id -u)/com.animalabs.termd` stops it for good. `termd --session-oom-score-adj N` sets how strongly the kernel prefers a session's processes over the daemon when memory runs out (default 200; 0 leaves it alone).

## CLI

`tsm [--scope NAME] COMMAND` calls the same eight tools: `tsm run main make test --wait 30`, `tsm look main --until end`, `tsm list`. `run`'s command is one argument as typed (`tsm run main 'make test | tee log'`), or several words, each quoted for the shell; put `--` before words that start with `--`. Use the agent's scope to see its sessions. Nothing `tsm` is shown counts as seen, so the agent is still told of it. `tsm --help` lists the rest.
