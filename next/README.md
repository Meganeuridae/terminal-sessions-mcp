# Terminal Sessions 2.0

> 2.0 lives in `next/`, beside the 1.x code this package has shipped so far. Both are in the package: `termd`, `tsm` and `tsm-relay` are 2.0; `terminal-sessions-mcp`, `session-server` and `session-cli` are 1.x. 2.0 changes what 1.x does in the ways [`CHANGELOG.md`](../CHANGELOG.md) lists: its graceful kill hangs up every process it lists on the session's terminal once the shell is gone, as `close` does, and three fixes. Otherwise, what reaches 1.x is the package they share: a narrower Node range (`engines`), `npm run build` and `npm test` building 2.0 too, and 2.0's two dependencies installing with it. The lockfile also moves `@types/node` from 20 to 22, and `express-rate-limit`, `hono` and `ip-address` up a patch release each. The design discussion is [antra-tess/terminal-sessions-mcp#11](https://github.com/antra-tess/terminal-sessions-mcp/pull/11).

Persistent shells for agents. Each session is your own login shell, kept alive by a daemon between calls, connections and host restarts. bash, zsh and fish start with your startup files and get the session's integration; any other shell starts with no arguments and runs without it (see [What it can't tell](#what-it-cant-tell)). An agent types into it only by explicit calls, gets the exit status, duration and directory of each command `run` types in an integrated shell, with its output (a command that ends the shell, such as `exit 17`, gets the shell's exit instead), and is woken only when something needs it: a command ended that no call was waiting on, a program is waiting for input, a shell died, or a pattern it asked for appeared.

It speaks MCP to any MCP host, and MCPL to hosts that support it (agent-framework, and Claude Code through `mcpl-cc-bridge`), for the wakes.

## Quick start

```bash
npm install -g term-sessions-mcp     # bins: termd, tsm, tsm-relay
tsm open demo
tsm run demo 'echo hello; pwd'
```

Then connect a host with one of the configurations in [`next/config/`](config/): each launches `tsm-relay` over stdio. Nothing needs to be started first: the first relay or `tsm` that finds no daemon starts one.

## What an agent gets

Nine tools. The results of `open`, `run`, `send`, `look`, `read`, `stop` and `integrate` open with the session's status line, such as `[main · command 3 · exit 0 · 1.2 s · at the prompt · /home/u/app]`: the command and how it ended, what is in front of the shell now, and the directory. `list` gives a line for each session, and `close` says how the shell ended. A refused call says why, and opens with the status line only when what is in front of the shell is the reason. When what is in front can't be read, as when `ps` or `stty` fails on macOS, `front.state` is `unknown` unless the shell's marks show it at its prompt. The status line then says the reading failed, and `run`, `integrate` and `stop` send nothing.

| Tool | |
|---|---|
| `open(name, cwd?, cols?, rows?)` | Opens a session. No other tool opens one, so a mistyped name is refused rather than run in a fresh shell. |
| `run(name, command, wait?, notify_on?)` | Runs one command line, only at the prompt; otherwise nothing is typed and the refusal says what is in front. Returns the status and output, or "still running" when the wait ends; on a host that takes wakes, the end is reported when it comes. `notify_on` reports a pattern in its output once: in the result if the command has ended, otherwise as it appears. Its `structuredContent` gives the same as values; see below. |
| `send(name, text?, keys?, paste?, wait_for?, wait?)` | Types exactly the text and named keys, nothing appended, for a program waiting for input or a full-screen one. A program such as Claude Code takes long typed text as a paste, and an Enter with it; `paste: true` sends the text inside the bracketed-paste frame and the keys after it, only while the program has turned bracketed paste on. Returns the new lines, or the screen, once `wait_for` matches or output is quiet. Arrows follow the cursor-key mode the program set. |
| `look(name, until?, match?, wait?)` | What you haven't seen yet, and what is in front now. While a full-screen program is up, its screen in place of the new lines; those come in the first `look` after it leaves. With `until: "end"`, `until: "input"` or `match`, after waiting for it. `until: "end"` also returns when a program in front waits for input, since it won't end until answered. |
| `read(name, command?, lines?, match?, context?)` | Earlier output: a command's output by id or a range of lines, not both, or matching lines with context, cut like every result, so long output is read in ranges. |
| `stop(name, signal?)` | Ctrl-C typed to the terminal, so it reaches whatever is in front, a shell's own loop included; then TERM, then KILL to the job in front, each step reported. TERM and KILL never go to the shell. With `signal`, any this system has, sent once to the job in front; a suspend signal such as TSTP stops the job and brings the prompt back, and `run fg` or `run bg` continues it. |
| `integrate(name, wait?)` | Gives the shell now in front the session's integration, typed: a shell reached through a typed `ssh`, `su` or `docker exec`, called at its prompt. bash, zsh and fish only. `run` then types there, with statuses, until that shell exits. |
| `list()` | Each session, what is in front of it, its directory, and reports you haven't seen. With many sessions, rows give way so the oldest report still shows. |
| `close(name, force?)` | Hangs up the shell and every process on its terminal when it lists them. A process started with `setsid` or `nohup` outlives it, and so does a group a job starts after that listing. `force` KILLs at once, and reaches the shell's descendants too. Its own steps end within 55 s of the call, under agent-framework's 60 s deadline for a call, and it names what it couldn't list or see exit by then. Returns the session's reports you haven't seen that fit its result, and `list` gives the rest. |

- **Waits** default to 15 s and stop at 55 s, under agent-framework's 60 s deadline for a call. A `read` search, and `run`'s `notify_on` search of output already there, stop at 55 s too, and say which lines they left. No call waits longer.
- **Starting a server** is one `run` with a short wait and a `notify_on` for what it prints when it's ready or when it fails: `run(name: "web", command: "npm run dev", wait: 5, notify_on: "listening|EADDRINUSE")`. If the server fails within the wait, the result gives its exit status and the matching line. If it's still running, the result says so. The first match then comes as a wake, even one printed during the wait, since the search starts at the command's first line. A host that takes no wakes, such as `tsm`, gets no report of that match: `look` with `match` waits for it instead.
- **A shell given the integration with `integrate`**, such as one inside `ssh`, has its state read from its marks. The session follows it only while the program it was reached through holds the terminal, itself or through a process it started, as a local shell's jobs do. Once that program ends or leaves the terminal, as when ssh exits or is suspended, the session stops following that shell, and a command it was running ends as no longer followed, with no status: it may run on. When no mark shows that program's end, as under a shell without the integration, or when a command follows it on the same line, the end is seen at the next call that looks. On Linux the session also looks every 250 ms while a command runs. A program on the far host is out of this terminal's sight. Say a far shell runs `ssh other; vim` as one line, and the shell on `other` is given the integration. Once that ssh ends, the marks still show the shell on `other` at its prompt, and `run` would type into `vim`. The far shell marks each line it runs, not each command on it. The status line names the program it runs within, as in `at the prompt of the shell within ssh box`, and so does `front.within` in `structuredContent`. The kernel sees only that program, so a far program never shows as waiting for input. `run` types its command inside a wrapper of under 200 characters that keeps its statuses, as one line of at most 8,192 characters, counting each `'`, `\`, `!`, control or non-ASCII byte of the command as five. `stop` types only Ctrl-C there, and refuses a `signal`, which would reach the local program. `integrate` is refused while this terminal reads whole lines, as at the password or yes/no questions ssh, su and sudo ask on this machine. A program that holds the terminal raw, such as a connected ssh, hides its far side: a question there can't be seen, and the probe line would answer it. At a far `sudo` password prompt, the probe line goes out as a password attempt. Call `integrate` once `look` shows the far prompt. After `integrated`, `look` starts at the far prompt, so the hooks' echo is skipped. The result first shows what `look` would have returned at the call's start, such as a login banner, and then anything the far shell printed while taking the hooks. If the wait runs out once the hooks are all typed, a prompt drawn later still completes it. In a shell that writes its history as it goes, the probe line reaches its history file, and in zsh so does the line that turns saving off. Nothing typed after them does. Text still on its way through `ssh` when a command ends can run as typed. `close` ends the local program; far jobs that outlive their own hangup are the far host's to end.
- **A cancelled call** answers nobody. What it took is reported as though no call had taken it. It isn't reported if another call's result showed it. Nor is it once a later report about its command has come. A wait for input that is over isn't reported. A call that fails after taking something reports it the same way. A cancelled `run`'s command keeps running, and its `notify_on` still reports.
- **Long output** keeps its start and its end within 24,000 characters, agent-framework's inline limit for a tool result, and says how to read more: `read` gives a command's output or a range of lines, cut the same way. A single line longer than that is cut in its middle, and no call returns the middle.
- **`run`'s `structuredContent`,** for a script, holds `command`, `front` and `running`, and:
  - `exitCode`: the command's status. It is `null` with `running: true` while the command runs, and `null` with `running: false` when no status is known: a shell without the integration, a removed hook, or the shell exiting mid-command. It is `null` with `running: false` and `unfollowed: true` when the session stopped following the shell the command ran in, as when the ssh that shell was reached through ended or was suspended: the command didn't end where the session could see it, and may still be running there. It is `null` with `stopped: true` when a `stop` signal stopped the job: what the shell reports then, such as 148 in bash on Linux or 0 in fish, isn't the job's exit status. A non-zero status is a result, not `isError`.
  - `output`: the command's own lines joined by `\n`, never the status line, the typed command or the text's notes. It is whole when it fits the budget the text has for it; otherwise it keeps the start (a third) and the end, and `outputLeftOut` gives `at`, where in `output` the left-out part belongs, and `characters`, how much was left out. Both count UTF-16 code units, as every budget here does, and the cut never splits a surrogate pair, so a script that indexes by code point is off by one for each character outside the Basic Multilingual Plane before `at`. `read` with a range of `lines` within the command's gives the rest, unless the cut is inside one line longer than the budget, whose middle no call returns. `outputDropped` counts the earliest lines the session no longer keeps, when there are any. While the command runs, `output` is what it has printed so far, and its last lines may still change on the screen. In a shell without the integration it holds the same lines the text shows, which the session ends at the shell's next prompt rather than at an end mark.
- **A full-screen program's screen** fits one result whole when each cell is one UTF-16 unit and the result's other lines fit the 1,000 characters kept for them. Wider text (emoji, combining marks), or many commands ending during one `send`, loses top rows, and the result says how many.
- **Wakes** (MCPL, feature set `terminal.events`) carry the status line and the last 20 lines or the screen, one tag each: `terminal:ended`, `terminal:waiting`, `terminal:exited`, `terminal:match`; a match's wake carries its matched line instead. A report no host took stays for `list` and `look`; one about a command goes once the session no longer keeps that command. When a caller that takes no reports, such as `tsm`, closes a session that a host taking reports has used, the session's reports stay for `list` and as wakes, with one more saying it was closed. They stay until such a host takes them: at most what the session held while open, and one. It keeps its last 10,000, and fewer when their text passes 6 Mi characters. Plain MCP hosts get no wakes; `look` with `until` is how they wait.
- **Scopes:** the relay's `--scope` names the sessions a host sees, so two agents' `main` are two shells. Two hosts given the same scope share its sessions and their wakes: a wake is pushed to each host not still answering an earlier one, and to a busy one later only if no host has taken it by then.
- **`close`** hangs up the shell and every process on its terminal, listed once. That includes disowned jobs and jobs whose parent exited, whatever the shell's own settings, such as zsh's `NO_HUP`. A process that left the terminal with `setsid` outlives it. So does a job started with `nohup`, which ignores the hangup. `close` with `force` KILLs the shell, every process on its terminal and every process the shell started. Only a process that left the terminal and is no longer the shell's descendant outlives it.
- **Environment:** every session's shell starts from the daemon's environment, minus the launching terminal's identity, Volta's and npm's launch variables, agent hosts' session variables and this package's own, with Volta's internal image directories taken off `PATH`, and it is the same for every scope. When the shipped unit or launch agent runs the daemon, or a relay starts it as a transient systemd unit, that is the user manager's or launchd's environment, not the relay's; when a relay or `tsm` starts it detached, it is the environment of whichever started it. Other state of whatever started it stays, such as an activated virtualenv's. The shell's startup files run on top of it. Scopes keep sessions apart, not credentials: they are one user's shells.

## What it can't tell

- **A shell without the integration** gives no statuses: it counts as at its prompt once its output is quiet and it waits at the terminal (its line editor holds it, or the shell reads it itself), and a command's status is "unknown". Output after a command's last line break shares a line with the next prompt, and is left out. A builtin `read` waiting at the terminal looks the same as the prompt there, so `run` types into it; answer it with `send`. The terminal may echo a multi-line command's later lines, and those can show in its output. Inside an `ssh` someone typed, what is in front is `ssh`, and what is typed there gets no statuses either, until `integrate` gives the shell there the integration (below). Or run the relay on the other machine, as in "Another machine, over ssh".
- **A command typed through `send` that removes both the session's prompt hook and its prompt mark** (`unset PROMPT_COMMAND; PS1="> "` in bash, `precmd_functions=(); PS1="> "` in zsh) leaves the session unable to see its prompt: it shows the shell itself running and refuses `run`. `close` the session and `open` it again. A command given to `run` in bash or zsh gets the hooks put back after it, except a zsh command that leaves a heredoc without its terminator (below). A command typed through `send` that removes only the prompt hook leaves the prompt seen, with that command's status unknown.
- **Waiting for input** is the kernel's evidence: on Linux, a program blocked reading this terminal. A program that waits in `poll`, such as Python's REPL or `ssh`, shows as running. So does a 32-bit program on a 64-bit Linux kernel: its system calls use another numbering. macOS shows no such evidence, so there it is always "running", and the status line says it can't tell.
- **End marks** carry a chained nonce: a mark's counter is spent once used, so output that replays an old mark is refused. A program that reads the shell's own variables can print a mark with the live nonce, deliberately, and is not defended against. Output never shows a recent nonce. It shows `[redacted]` in its place, padded with dots to the nonce's length.
- **A daemon restart ends every shell.** A host that reconnects is told no session it names is open.
- **bash isn't started in login mode,** since a login bash ignores the file that installs the session's hooks. It reads the files a login shell reads, in their order (`/etc/profile`, then the first of `~/.bash_profile`, `~/.bash_login` and `~/.profile`), but `shopt login_shell` is off and `~/.bash_logout` doesn't run. zsh and fish start as login shells.
- **On macOS, reading what's in front can spawn `ps`, synchronously.** Under heavy load, `list` over many sessions holds the daemon, and every call's answer, for the sum of those reads.
- **fish 3 keeps a command given to `run` out of its history.** fish 4 adds it, as typing it would.
- **In zsh, a heredoc left without its terminator** in a command given to `run` takes the session's own lines after it as its body: they print, or go into the file the heredoc writes, and the hooks aren't put back after that command.
- **In bash, while a command given to `run` runs,** its RETURN trap is the session's, which keeps the pipeline's statuses. `trap -p RETURN` shows it there, and the shell's own trap comes back afterwards.

## Coming from 1.x

1.x's nine tools, and what 1.x offered scripts, map to 2.0 like this.

| 1.x | 2.0 |
|---|---|
| `launch` | `run` with a short `wait` and a `notify_on` for the program's ready and error lines, as in "Starting a server" above. |
| `runCommand` | `open`, then `run`. No tool opens a session for you, so after a daemon restart a command isn't run in a fresh shell. |
| `listSessions` | `list`. |
| `tailLogs` | `read`, for a command's output or a range of lines, or `look`, for what you haven't seen and what is in front. |
| `searchLogs` | `read` with `match` and `context`. |
| `sendInput` | `send`, with `text` and `keys`. |
| `sendSignal` | `stop`. Its TERM and KILL go to the job in front, never to the shell. Its Ctrl-C reaches whatever reads the terminal, a loop in the shell included. 1.x sent every signal but SIGINT to the shell itself. |
| `killSession` | `close`. A graceful close ends the same processes as 1.x's graceful kill. With `force`, 2.0 also KILLs every process on the terminal and the shell's descendants. 1.x's forced kill KILLs the shell alone. |
| `killAll` | Not carried. `list`, then `close` each. One call ending every session in a scope could end another agent's sessions where two share a scope. |
| `raw: true` | Not carried. `look` gives a full-screen program's screen, and the escape codes would be noise. |
| The WebSocket API and `SessionClient` | Not carried. A script uses the MCP tools, or `tsm --json`, which prints a result's `structuredContent` alone. Some results carry their content only in their text: `read`'s lines, the new lines `look`, `send` and `integrate` return, and a full-screen program's screen. For those, a script reads the text, which `tsm` prints without `--json`. |
| Resizing a session, through the WebSocket API's `session.resize` | Not carried. `open` a session with the `cols` and `rows` it needs. A resize reflows the lines the session keeps, so line numbers and positions already returned would point at other text. |
| Windows, where 1.x's sessions ran `wsl.exe` | The relay and daemon run inside a WSL2 distro, as in "Windows, through WSL2" below. |
| The network server and its `--token` | Not carried: 2.0 opens no port. For another machine, the host starts the relay there over ssh, as in "Another machine, over ssh" below. |

## Running the daemon

One daemon per user holds every shell, on a Unix socket in a directory only you can enter: `$XDG_RUNTIME_DIR/terminal-sessions/daemon.sock`; where that variable isn't set, `/run/user/<uid>/terminal-sessions/daemon.sock` on Linux when that directory is yours alone; otherwise `/tmp/terminal-sessions-<uid>/daemon.sock`. A relay that finds none starts one: on Linux, as a transient systemd user unit where one can be started, so the daemon outlives a host whose service stops; elsewhere, or where `systemd-run` fails, detached, in the starter's control group, with its output in `daemon.log` beside the socket. To have it started again after a crash, install `next/config/termd.service` (systemd) or `next/config/com.animalabs.termd.plist` (launchd). Either keeps the daemon across logins only where the user's service manager outlives a logout, which on Linux takes lingering (`loginctl enable-linger`); on macOS a launch agent stops at logout. Start the systemd unit (`systemctl --user enable --now termd`) before any relay starts a daemon, or after `tsm daemon stop`. Its daemon exits when it finds another already answering, and `Restart=on-failure` doesn't start it again. The launch agent's `KeepAlive` starts it again every 10 seconds, so it takes over once the other daemon ends.

`tsm daemon stop` asks it over its socket to stop, ending every shell, and returns once the socket no longer answers; it sends no signal, and names the daemon's pid if it doesn't stop. Under the shipped launch agent, launchd starts it again (`KeepAlive`); `launchctl bootout gui/$(id -u)/com.animalabs.termd` stops it for good. `termd --session-oom-score-adj N` sets how strongly the kernel prefers a session's processes over the daemon when memory runs out (default 200; 0 leaves it alone).

### Another machine, over ssh

A host reaches another machine's daemon by launching the relay there over ssh: `"command": "ssh", "args": ["-T", "-o", "BatchMode=yes", "box", "tsm-relay", "--scope", "AGENT"]`.

- **The relay's stdout is the protocol.** A startup file on the far machine that prints for a command run over ssh, such as a `.bashrc` that echoes, breaks it.
- **`PATH`:** a command run over ssh gets no login shell, so a `tsm-relay` that nvm or Volta installed isn't found. Give node's absolute path then, and the relay's after it: `/path/to/node /path/to/term-sessions-mcp/next/dist/src/relay.js --scope AGENT`.
- **`BatchMode=yes`** turns a password or host-key prompt into a failure the host sees, rather than a wait.
- **The far daemon lives as long as the far user's service manager.** On Linux, the relay starts it as a transient systemd user unit. Without lingering (`loginctl enable-linger`), the manager stops when the user's last login session ends. The daemon and every shell go with it.
- **A dropped connection** ends the relay and any call in flight; the relay never reconnects. The far daemon and its sessions live on, and a relay the host starts again finds them.
- **A far macOS machine** has no systemd. Its daemon should come from the launch agent ([`config/README.md`](config/README.md)). The ssh route to macOS is untested.
- Tested on Ubuntu 26.04 with Node 22, over ssh to the same machine: a command's status and output, a result cut to the 24,000-character limit, a command's end pushed through ssh, and a session kept across a dropped connection.

### Windows, through WSL2

On Windows, a host launches the relay inside a WSL2 distro: `"command": "wsl.exe", "args": ["-d", "Ubuntu-24.04", "-u", "me", "-e", "/path/to/node", "/path/to/term-sessions-mcp/next/dist/src/relay.js", "--scope", "AGENT"]`.

- **`-e` runs the relay with no shell between,** so nothing a startup file prints reaches the protocol. With no login shell, `PATH` has no node that nvm or a tarball put elsewhere, so give node's absolute path and the relay's.
- **`-u`** names the user the relay, the daemon and every shell run as.
- **WSL stops an idle distro, and every session's shell with it.** Microsoft documents the default as 15 seconds (`instanceIdleTimeout`). In our run, the distro stopped 10 to 20 seconds after the last `wsl.exe` client left, though systemd ran and the user was lingering. `instanceIdleTimeout=-1` under `[general]` in `%UserProfile%\.wslconfig` kept it running through a 60-second gap, and the session with it. That file applies to every distro. `wsl --shutdown`, the quick way to apply it, stops every running distro. Another `wsl.exe` client kept attached, such as `wsl.exe -d Ubuntu-24.04 -e sleep infinity`, also kept it running, and changes nothing else.
- **Paths** in `open`'s `cwd` are the distro's. Windows' drives are under `/mnt/c` and so on.
- Tested on GitHub's windows-2025 runner, with WSL 3.0.3, Ubuntu 24.04 and Node 22: a command's status and UTF-8 output, a result cut to the 24,000-character limit, a command's end pushed through `wsl.exe`, and the idle stop with and without what keeps it up.

## CLI

`tsm [--scope NAME] COMMAND` calls the same nine tools: `tsm run main make test --wait 30`, `tsm look main --until end`, `tsm list`. `run`'s command is one argument as typed (`tsm run main 'make test | tee log'`), or several words, each quoted for the shell; put `--` before words that start with `--`. Use the agent's scope to see its sessions. Nothing `tsm` is shown counts as seen, so the agent is still told of it. `tsm --json` prints the result's `structuredContent` as one line of JSON instead of its text, for a script. A refusal's JSON names its `error`, and its words go to stderr. `tsm --help` lists the rest.
